# FieldGrade sample data

Offline inputs so every module can be exercised without hardware, without network,
and without the (still-missing, and proprietary) `sp6b.gps`.

Each file is labelled **REAL** or **SYNTHETIC**. Never let a synthetic file be
mistaken for evidence: synthetic data proves the *code path*, never the *system*.

## design/

| File | Origin | Kind |
|---|---|---|
| `bratton_farm.xml` | landxml.org LandXML-2.0 Carlson Software samples | **REAL** |
| `nunosurf.xml` | landxml.org LandXML-2.0 Carlson Software samples | **REAL** |
| `landxml_road.xml` | github.com/mac999/landxml_parser | **REAL** (negative fixture) |
| `nunosurf_design.xyz` | derived from `nunosurf.xml` (see below) | **REAL** geometry, re-encoded |

Downloaded from <http://www.landxml.org/webapps/landxmlsamples.aspx>.
LandXML is an open, published schema — no reverse engineering.

- `nunosurf.xml` — 7,048 pts / 12,798 faces, **227 x 196 m (~4.4 ha), 0.61 m relief**.
  Near-flat: the **land-levelling design surface** stand-in, and the surface the
  simulation grades to.
- `bratton_farm.xml` — 14,424 pts / 28,549 faces, ~113 ha, 65.2 m relief.
  A real surveyed farm; the **rolling existing-ground** stand-in, and the large-file
  parser test.
- `landxml_road.xml` — valid LandXML containing only a road alignment and **no
  surface at all**. Kept so the reader is tested on refusing input it cannot honour.

### LandXML gotchas — each verified against these files, not assumed

1. `<P id="n">` payload order is **north east elevation**, not east/north.
   Reading it the other way mirrors the field about a diagonal.
2. `<P>` ids are **not contiguous** — `nunosurf` has 7,048 points running to id
   7063. Faces reference *ids*, so `index = id - 1` silently attaches triangles
   to the wrong vertices and yields a plausible, wrong surface.
3. **Units are declared per file and differ between these two.** `bratton_farm`
   is `<Metric linearUnit="meter">`; `nunosurf` is
   `<Imperial linearUnit="USSurveyFoot">`. Treating survey feet as metres inflates
   the field by 3.28x. The reader converts to metres and refuses unknown units.
4. `<F>` indices are 1-based; a face may carry `i="1"` marking it deleted.

`nunosurf_design.xyz` is the same real surface re-encoded as the XYZ text
interchange the industry moves designs in
(`Point,Easting,Northing,Elevation,Code` — the OptiSurface -> Topcon AgForm3D
format), converted to metres and shifted so the field's min corner is the local
origin. Geometry unchanged and real.

Regenerate with:

```bash
python tools/landxml_to_xyz.py tools/sampledata/design/nunosurf.xml \
       tools/sampledata/design/nunosurf_design.xyz --local
```

## nmea/

| File | Origin | Kind |
|---|---|---|
| `amod_agl3080_consumer.txt` | github.com/esutton/gps-nmea-log-files | **REAL** |
| `site_track_rtk.nmea` | generated by `tools/make_rtk_track.py` | **SYNTHETIC** |

- `amod_agl3080_consumer.txt` — REAL consumer-grade log (AMOD AGL3080, 2012),
  2,835 lines. Contains `$ADVER`, GSA, GSV, VTG, a truncated tail, and fix
  qualities 0/1/2 — no-fix at power-up, autonomous, then DGPS.
  Its job is to prove the parser survives real-world mess. It is **not** usable
  for guidance: nothing in it can pass the RTK-FIXED gate, which is itself
  asserted by a test.

- `site_track_rtk.nmea` — SYNTHETIC RTK track: GGA quality 4 + GST + RMC at 5 Hz,
  4,052 epochs (~13.5 min) of serpentine field work over `nunosurf`.
  **No public RTK-fixed agricultural NMEA log could be found**, so this is
  generated. Replace it the moment a real Emlid recording exists — that is a
  Tier-B gate, not a Tier-A one.

Regenerate with:

```bash
python tools/make_rtk_track.py tools/sampledata/design/nunosurf_design.xyz \
       tools/sampledata/nmea/site_track_rtk.nmea --swath 20
```

### What the generated track does and does not model

Models: a continuous serpentine pass clipped to the surveyed **convex hull** (a
Delaunay TIN covers exactly its hull, so that is the true field boundary, and an
occupancy grid is *not* a valid substitute here — these survey points lie along
contour lines, leaving most cells between contours empty); ground that is the
design plane plus smooth deterministic undulation, so there is real cut/fill work;
an antenna on a 3.10 m mast above the blade.

Does **not** model: multipath, RTK dropout to FLOAT, correction-age spikes,
satellite geometry changes, wheel slip, machine pitch and roll. Pitch is the
significant omission — at a 3.10 m mast, 1 degree of pitch moves the derived blade
elevation by ~54 mm, which is twice the working tolerance.

One assumption worth stating: the generator writes orthometric height plus a geoid
separation that the parser adds straight back, so ellipsoidal height returns in
the **same datum as the design**. That models a receiver already outputting heights
on the site datum. A receiver that does not leaves a large constant offset, which
is what bench-in exists to remove — covered separately by
`benching_in_removes_a_vertical_datum_offset`.
